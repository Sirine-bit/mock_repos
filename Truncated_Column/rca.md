# Gold RCA

## Scenario
The requirements ingestion job extracts data successfully, then fails when inserting into SQL Server because the runtime database column `assigned_to` is narrower than the value generated by the ETL.

## Terminal Failure
- Stage: `Get_Requirements_Ipnext`
- Correct class: `CODEBASE_ISSUE`
- Terminal error: string/binary data would be truncated in column `assigned_to`

## Root Cause In This Fixture
The extractor in [ingestion/jobs/codebeamer_ingestion/data_access/extract_requirements_ipnext.py](./ingestion/jobs/codebeamer_ingestion/data_access/extract_requirements_ipnext.py) collapses many assignees into one long comma-separated string. The local repo schema artifacts are intentionally stale and suggest `assigned_to` is wide enough, but the real SQL Server table is narrower. Because [ingestion/jobs/codebeamer_ingestion/infra/db_connector.py](./ingestion/jobs/codebeamer_ingestion/infra/db_connector.py) inserts the dataframe unchanged with `to_sql()`, the job fails only when the live database schema is consulted at runtime.

## Defective Location
- Primary file: `ingestion/jobs/codebeamer_ingestion/data_access/extract_requirements_ipnext.py`
- Runtime confirmation source: live SQL Server metadata for `raw_requirements_ipnext_codebeamer_daily.assigned_to`
- Defect type: `logic_error` / schema-size mismatch

## Evidence The Agent Should Use
- [ingestion/jobs/codebeamer_ingestion/pipelines/get_requirements_ipnext.py](./ingestion/jobs/codebeamer_ingestion/pipelines/get_requirements_ipnext.py) shows the insert flow.
- [ingestion/jobs/codebeamer_ingestion/data_access/extract_requirements_ipnext.py](./ingestion/jobs/codebeamer_ingestion/data_access/extract_requirements_ipnext.py) shows the long joined `assigned_to` value.
- [ingestion/jobs/codebeamer_ingestion/infra/db_connector.py](./ingestion/jobs/codebeamer_ingestion/infra/db_connector.py) confirms raw `to_sql()` insertion and states that live SQL Server metadata is authoritative.
- [ingestion/jobs/codebeamer_ingestion/db/schema.py](./ingestion/jobs/codebeamer_ingestion/db/schema.py) and [sql/schema/raw_requirements_ipnext_codebeamer_daily.sql](./sql/schema/raw_requirements_ipnext_codebeamer_daily.sql) are stale local references and should not be treated as proof of the runtime column width.

## Mandatory Database Verification
A strong investigator must query the actual database schema before concluding the root cause. Static repo inspection alone is not sufficient for full credit.

Minimum checks:
1. Query `INFORMATION_SCHEMA.COLUMNS` for `raw_requirements_ipnext_codebeamer_daily`.
2. Confirm the live `assigned_to` column length is smaller than the produced value.
3. Optionally compute the generated string length from the ETL sample data and compare it to the live column width.

## How The Agent Should Reason
1. Start from the SQL truncation error and capture the column name: `assigned_to`.
2. Inspect the ETL code to see how `assigned_to` is produced.
3. Notice the repo does not provide a trustworthy production schema source.
4. Query the live database metadata to get the real `assigned_to` length.
5. Compare produced value length against the queried live width.
6. Conclude the root cause is an oversized transformed value hitting a narrower runtime schema than the repo suggests.

## What A Strong Answer Must Say
- The failing column is `assigned_to`.
- The extractor builds an oversized comma-separated string.
- The decisive confirmation comes from querying the live database schema, not from the stale local schema files.
- The runtime `assigned_to` width is smaller than the generated value, which explains the truncation error.

## What Should Be Marked Wrong
- Treating the local schema files as authoritative proof of the runtime width.
- Blaming the database connector alone without mentioning the oversized field and live schema mismatch.
- Calling this an infrastructure outage.
- Giving full confidence without any database metadata verification.
